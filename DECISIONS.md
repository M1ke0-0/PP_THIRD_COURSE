# Почему мы выбрали именно это решение

Документ объясняет каждое крупное решение в проекте: что выбрали, какие были альтернативы и почему они не подошли.
Пригодится на защите и при спорах в команде.

---

## Коротко

| Вопрос | Выбор | Главная причина |
|---|---|---|
| Как защищать тест | Свой клиент-киоск + блокировка на уровне Linux | У Safe Exam Browser нет клиента для Linux |
| На чём клиент | Electron | Встроенный kiosk mode, полный контроль над навигацией и запросами, много документации |
| Как блокировать систему | Отдельный пользователь + оболочка `cage` | Только ОС может заблокировать Alt+Tab и переключение консолей |
| Бэкенд | Django | Задание требует Python; админка, авторизация, ORM и защита из коробки |
| Интерфейс | Шаблоны Django + Bootstrap | Меньше кода, клиент просто открывает страницы сервера |
| Где сервер | Один университетский сервер | Правильные ответы не попадают на компьютер студента |
| База данных | SQLite для разработки, PostgreSQL для продакшна | Ноль настройки при разработке, надёжность на сервере |

---

## 1. Почему не взять Safe Exam Browser как есть

SEB — лучший готовый инструмент для экзаменов, и на Windows и macOS мы бы использовали его. Но:

- **Клиента для Linux нет.** Есть версии для Windows, macOS и iOS.
- **Портировать SEB на Linux нереально в рамках курсового.** Блокировка в SEB написана под конкретную ОС:
  на Windows — C# и системные вызовы Windows (своя изолированная оболочка), на macOS — Objective-C и режим Assessment Mode от Apple.
  Для Linux это не адаптация, а написание нового приложения с нуля.
- **SEB Server нам не нужен.** Он предназначен для связки SEB с готовыми LMS (Moodle, Open edX). У нас своя система тестирования.

Что мы всё-таки берём от SEB: идею проверки клиента на сервере. Сервер пускает к тесту только запросы
от защищённого клиента. При желании наш сервер сможет принимать и официальный SEB на Windows/macOS по его ключам.

---

## 2. Почему не Moodle + SEB

Если в университете уже есть Moodle, то Moodle Quiz + SEB на Windows — самый дешёвый способ провести защищённый тест.
Мы этот вариант не выбираем, потому что:

- задание курсового — разработать **собственную** информационную систему тестирования (`prompt.md`);
- проблема Linux никуда не девается: SEB для Linux нет и в связке с Moodle.

На защите это стоит сказать прямо: мы знаем про готовое решение, но цель проекта — сделать своё и закрыть дыру с Linux.

---

## 3. Почему не коммерческий прокторинг (Proctorio, ProctorU, Examus и т.п.)

- **Платно**, обычно за каждого студента или экзамен.
- **Персональные данные.** Такие сервисы записывают веб-камеру, экран и микрофон и хранят записи у себя.
  Для университета это вопросы по 152-ФЗ и согласиям студентов.
- **Зависимость от внешнего сервиса.** Нет интернета или сервис упал — экзамена нет.
- **Linux** поддерживается слабо или не поддерживается.
- Это не разработка, а покупка — не подходит для курсового проекта.

---

## 4. Почему не просто браузер в режиме киоска

Самый простой вариант — `firefox --kiosk https://exam...`. Почему мы на нём не остановились:

- **Сервер не отличит его от обычного браузера.** Студент откроет тот же адрес в обычном Chrome на другом компьютере
  и пройдёт тест без защиты. Нашему клиенту мы можем добавить свой заголовок, а сервер будет пускать только его.
- **Сложно управлять поведением.** Запретить переход на чужие сайты, новые окна, DevTools, выход до конца теста
  в Firefox можно только через корпоративные политики (`policies.json`) — это громоздко и разбросано по настройкам.
- **Нельзя добавить свою логику**: например, выход только после завершения теста или по паролю администратора.

Честно: Firefox с корпоративными политиками — рабочая лёгкая альтернатива. Мы выбрали свой клиент,
потому что он даёт контроль над каждым запросом и выходом, а код клиента — часть нашего проекта, его можно показать и объяснить.

## 5. Почему Electron, а не другие варианты клиента

| Вариант | Плюсы | Почему не выбрали |
|---|---|---|
| **Electron** (выбран) | Готовый `kiosk: true`; контроль навигации, новых окон, горячих клавиш, заголовков; одинаковый Chromium на всех ОС; огромное количество примеров | Большой размер (~100+ МБ), много памяти |
| PyQt6 + QtWebEngine | Всё на Python, как и бэкенд | Меньше готовых примеров для киоска, сложнее собрать пакет под Linux, больше ручной работы с горячими клавишами |
| Tauri | Маленький размер, быстрый | Нужен Rust; на Linux использует WebKitGTK, который ведёт себя иначе, чем Chromium |
| Свой браузер на C++ (CEF) | Максимальный контроль | Слишком сложно для курсового |

Размер Electron для экзаменационного клиента не критичен: он ставится один раз на компьютеры аудитории.

## 6. Почему блокировка на уровне Linux, а не только в приложении

Ни одно приложение — ни Electron, ни браузер — не может само заблокировать системные комбинации:

- **Alt+Tab** обрабатывает оконный менеджер, а не приложение;
- **Ctrl+Alt+F1…F12** (переключение консолей) обрабатывает ядро и systemd;
- **Ctrl+Alt+Del**, меню рабочего стола, уведомления — тоже система.

Поэтому защита состоит из двух слоёв:

1. **Приложение** закрывает всё внутри окна: другие сайты, новые окна, DevTools, правый клик, горячие клавиши браузера.
2. **ОС** убирает всё снаружи: отдельный пользователь `exam` с автовходом, который запускает клиент в оболочке `cage`.
   `cage` показывает ровно одно приложение на весь экран — Alt+Tab переключать некуда, рабочего стола нет.

Почему `cage`, а не GNOME или KDE в режиме киоска: `cage` создан ровно для этой задачи, у него нет панелей, меню
и настроек, которые нужно отключать. Чем меньше в системе возможностей, тем меньше способов их обойти.

## 7. Почему Django

**Главное:** задание (`prompt.md`) требует Python и Django 5. Но выбор оправдан и сам по себе:

| Что нужно по заданию | Что даёт Django из коробки |
|---|---|
| Роль администратора: пользователи, тесты, результаты | Готовая админ-панель `/admin/` |
| Регистрация, вход, смена и восстановление пароля | `django.contrib.auth` |
| Реляционная база, миграции | ORM и система миграций |
| Защита CSRF, серверная валидация | Встроенный CSRF, формы с валидацией |
| Страницы с Bootstrap | Шаблонизатор |
| Небольшой REST API | Django REST Framework |
| Автотесты | Встроенный тестовый фреймворк с тестовой базой |

### Сравнение с альтернативами

| Фреймворк | Что пришлось бы делать самим |
|---|---|
| **FastAPI** | Админку, авторизацию с ролями, сессии, CSRF, восстановление пароля. ORM (SQLAlchemy) и миграции (Alembic) подключать отдельно. Интерфейс — отдельным фронтендом |
| **Flask** | Почти то же, что FastAPI: всё собирается из отдельных расширений |
| **Node.js / Express** | Не Python — не подходит под задание |

FastAPI отлично подходит для быстрых API и микросервисов. Но у нас информационная система с ролями, формами и админкой —
это ровно то, для чего делали Django. На FastAPI тот же функционал займёт заметно больше времени.

**Про ветку main:** в репозитории уже есть каркас на FastAPI + React. Если команда решит остаться на нём,
вся логика защиты (киоск, `cage`, проверка клиента на сервере, журнал событий) переносится без изменений —
от фреймворка зависит только серверная часть.

## 8. Почему шаблоны Django, а не React

- Задание требует HTML, CSS, Bootstrap 5 и JavaScript — отдельный фронтенд-фреймворк не нужен.
- Один проект вместо двух: не нужно отдельно собирать, разворачивать и синхронизировать фронтенд и бэкенд.
- Клиент-киоск просто открывает страницы сервера. С SPA пришлось бы дополнительно настраивать CORS и токены.
- Проверка прав в шаблонах на сервере: студент физически не получает HTML страниц, которые ему недоступны.

React имел бы смысл для сложного интерактивного интерфейса. Страница вопроса с таймером и кнопками «Назад / Далее»
делается обычным JavaScript.

## 9. Почему один центральный сервер

Альтернатива — ставить Django на каждый компьютер аудитории. Мы от неё отказались:

- **Утечка ответов.** База с правильными ответами окажется на компьютере студента.
- **Время.** Таймер на сервере нельзя обмануть переводом часов на компьютере студента.
- **Результаты в одном месте.** Преподаватель видит всё сразу, ничего не нужно собирать с каждой машины.
- **Обслуживание.** Обновить один сервер проще, чем тридцать компьютеров.

Минус — нужна сеть в аудитории. Ответы сохраняются после каждого вопроса, поэтому кратковременный обрыв сети не теряет данные.

---

## 10. Почему SQLite и PostgreSQL

- **SQLite при разработке:** ничего не нужно ставить, база — один файл, можно удалить и пересоздать.
- **PostgreSQL на сервере:** нормально работает, когда десятки студентов одновременно отправляют ответы; надёжные резервные копии.
- Переключение — через переменные в `.env`, код не меняется: Django ORM одинаково работает с обеими базами.

## 11. Что наше решение не защищает (и это нормально)

На защите лучше назвать ограничения самим, чем ждать вопроса:

- **Телефон и бумажная шпаргалка** — программно не решается ни нами, ни SEB, ни платным прокторингом без камеры.
- **Виртуальная машина** — SEB умеет её обнаруживать, мы нет. В аудитории у студента нет прав запустить VM.
- **Свой ноутбук студента** — без киоск-сеанса работает только защита внутри окна; сервер записывает каждую потерю фокуса.
- **Ключ клиента можно извлечь** из приложения — смягчаем сменой ключа перед сессией и списком разрешённых IP аудитории.

Цель системы — не сделать списывание невозможным (это невозможно), а убрать простые способы и оставить след в журнале для остальных.
