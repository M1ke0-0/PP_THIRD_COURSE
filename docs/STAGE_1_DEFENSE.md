# Текст защиты первой стадии

На первой стадии проектного практикума мы сформировали техническое задание и заложили архитектурную основу системы онлайн-тестирования.

Цель проекта — создать универсальное веб-приложение, в котором преподаватель сможет создавать группы, вопросы и тесты, а студент — проходить назначенные тесты и получать результаты. В системе предусмотрены две роли: преподаватель и студент. Ключевые требования — разграничение доступа, автоматическая проверка, ограничение времени и числа попыток, сохранение ответов и статистика.

До начала реализации мы определили технологический стек. Клиентская часть строится на React и Vite. Для компонентов используется Material UI, за маршрутизацию отвечает React Router, а за обращения к API — Axios. Серверная часть строится на FastAPI с Pydantic; на следующих этапах подключаются SQLAlchemy и PostgreSQL. Обмен между frontend и backend выполняется по REST API в формате JSON.

Мы выбрали архитектуру модульного монолита. Она достаточно простая для учебного проекта, но позволяет разделить ответственность между слоями. React-приложение отвечает за интерфейс, FastAPI — за бизнес-логику, авторизацию и проверку прав, PostgreSQL — за постоянное хранение данных. Отдельные микросервисы на данном масштабе не требуются.

В рамках первой backend-задачи создана структура FastAPI-приложения. Конфигурация вынесена в отдельный модуль и читается из переменных окружения. Подключен CORS для локальной разработки, создан общий API-router и endpoint `GET /api/health`. Для него описана Pydantic-схема ответа и автоматический тест. Также FastAPI автоматически предоставляет Swagger UI, что будет удобно для согласования и демонстрации API.

В рамках первой frontend-задачи инициализировано React/Vite-приложение. Подключены Material UI, React Router и Axios. Созданы общая тема, точка подключения провайдеров, отдельная конфигурация маршрутов, стартовая страница, страница 404 и единый HTTP-клиент. Адрес backend задается переменной окружения, поэтому компоненты не зависят от конкретного адреса сервера.

Мы сразу зафиксировали несколько важных архитектурных решений из ТЗ. Проверка ролей будет выполняться на backend. Источником истины для таймера будет сервер. Сформированный вариант теста будет сохраняться и не изменяться при обновлении страницы. Ответы студента будут сохраняться на backend, а правильные ответы не будут передаваться клиенту до завершения попытки.

Таким образом, результат первой стадии — согласованное ТЗ, описанная архитектура и два запускаемых каркаса приложения. Эта основа позволяет frontend- и backend-разработке продолжаться параллельно по заранее согласованному API-контракту. Следующими задачами станут подключение PostgreSQL и SQLAlchemy на backend, а также layout и маршрутизация по ролям на frontend.
