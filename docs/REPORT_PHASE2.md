# Отчёт по фазе 2. Сервер: модели и защита

**Проект:** система онлайн-тестирования (Django) с защищённым клиентом-киоском для Linux
**Этап:** фаза 2 плана [EXAM_SECURITY_INTEGRATION.md](../EXAM_SECURITY_INTEGRATION.md)
**Дата:** 28.10.2026
**Итог:** фаза выполнена. Сделаны модели БД, серверные проверки, REST API и журнал событий; 37 автотестов проходят.

---

## 1. Задача этапа

1. Спроектировать базу данных по заданию (`prompt.md`, раздел 4): тесты, вопросы, варианты ответов, попытки, ответы студентов, учебные группы.
2. Добавить модели для защиты экзамена: журнал событий `ExamEvent` и флаг теста «только из защищённого клиента».
3. Реализовать все проверки прохождения теста **на сервере**, чтобы их нельзя было обойти из браузера.
4. Сделать REST API, через которое студент проходит тест.

## 2. Что сделано

| Часть | Файлы | Содержание |
|---|---|---|
| Модели | `testing/models.py`, `study_groups/models.py`, `attempts/models.py` | Test, Question, AnswerOption, TestGroup, Group, GroupStudent, Attempt, StudentAnswer, ExamEvent |
| Проверка клиента | `attempts/security.py` | Ключ клиента в заголовке `X-Exam-Client-Key`, сравнение за постоянное время |
| Бизнес-логика | `attempts/services.py` | Начало попытки, сохранение ответа, проверка и подсчёт баллов, таймер, журнал |
| API | `api/` | Сериализаторы, права доступа, представления, обработка ошибок |
| Админ-панель | `*/admin.py` | Все модели; у попытки видны ответы и журнал событий |
| Команды | `seed_data`, `expire_attempts` | Демо-данные; закрытие просроченных попыток по cron |
| Автотесты | `attempts/tests.py` | 37 тестов на все правила этапа |
| Клиент | `electron-app/main.js` | Клиент отправляет ключ в заголовке, но только на сервер тестирования |

Вся логика находится в `services.py`. Представления API только вызывают сервис и возвращают ответ (требование `prompt.md`, раздел 26).

## 3. Структура базы данных

```mermaid
erDiagram
    User ||--o{ Test : "создаёт"
    User ||--o{ GroupStudent : ""
    Group ||--o{ GroupStudent : ""
    Group ||--o{ TestGroup : ""
    Test ||--o{ TestGroup : ""
    Test ||--o{ Question : ""
    Question ||--o{ AnswerOption : ""
    Test ||--o{ Attempt : ""
    User ||--o{ Attempt : "проходит"
    Attempt ||--o{ StudentAnswer : ""
    StudentAnswer }o--o{ AnswerOption : "выбранные варианты"
    Attempt ||--o{ ExamEvent : "журнал"
```

Особенности схемы:

- **`Test.require_kiosk`**: если флаг включён, тест можно начать и проходить только из клиента-киоска.
- **`StudentAnswer.selected_answers`** — связь «многие ко многим». Так хранятся вопросы с несколькими правильными ответами.
- **`Attempt.max_score`** сохраняется при завершении попытки. Если преподаватель потом изменит тест, старые результаты не пересчитаются.
- **Одна активная попытка на студента** закреплена в самой базе (`UniqueConstraint` с условием `status = IN_PROGRESS`). Даже два одновременных запроса не создадут две попытки.
- **Журнал `ExamEvent`** хранит пять типов событий. Клиент может присылать только `FOCUS_LOST` и `NAVIGATION_BLOCKED`, остальные события создаёт сервер.

## 4. Серверные проверки

| Правило | Где проверяется | Ответ API | Скриншот |
|---|---|---|---|
| Тест только из киоска | `start_attempt`, `check_client` | 403 + событие `NOT_KIOSK` | 7, 16 |
| Тест опубликован и назначен группе студента | `Test.objects.available_for`, `start_attempt` | 404 | — (автотест) |
| Проходить тест может только студент | `IsStudent` | 403 | 21 |
| Не больше `max_attempts` попыток | `start_attempt` | 400 | 19 |
| Одна активная попытка; повторный вход продолжает её | `start_attempt` + ограничение в БД | 200 + `SECOND_SESSION` | 9 |
| Вариант ответа относится к этому вопросу | `save_answer` | 400 | 11 |
| В вопросе SINGLE выбран ровно один вариант | `save_answer` | 400 | 12 |
| Время считается по часам сервера; после дедлайна статус EXPIRED | `expire_if_overdue` | 400 + `TIME_EXPIRED` | 13, автотест |
| Завершённую попытку изменить нельзя | `ensure_in_progress` | 400 | 18 |
| Чужая попытка не видна | фильтр `student=request.user` | 404 | 20 |
| Правильные ответы не передаются студенту | `OptionSerializer` без `is_correct` | — | 8 |
| Клиент не может подделать серверное событие | `record_client_event` | 400 | 15 |
| CSRF | `SessionAuthentication` DRF | 403 | — |

## 5. Демонстрация работы

Сценарий выполнен на живом сервере (`runserver`) с демо-данными из `seed_data`. Все запросы и ответы на скриншотах — настоящие ответы сервера. Окна «обычного браузера» и «киоска» используют одну и ту же учётную запись `student`. Отличие только в одном: киоск отправляет заголовок `X-Exam-Client-Key`.

## 7. Как воспроизвести

```bash
source venv/bin/activate
cd backend
python manage.py migrate
python manage.py seed_data
python manage.py test
python manage.py runserver
```

После этого откройте `/admin/` (admin / admin12345) или `/api/` (student / student12345). Для запросов от имени киоска нужен заголовок `X-Exam-Client-Key: dev-kiosk-key`. Клиент `electron-app` отправляет его сам.

## 8. Ограничения и что дальше

- **Ключ клиента** можно извлечь из сборки клиента. Поэтому ключ меняется перед каждой сессией экзаменов; дополнительная мера — список разрешённых IP аудитории. Об этом риске сказано в разделе 11 плана.
- **Проверка ключей официального SEB** (раздел 7 плана) пока не сделана. Это необязательное расширение, на него нужно 1–2 дня.
- **Страниц для студента и преподавателя** пока нет. Тест проходят через API, данные смотрят в админке. Страницы — следующие этапы `prompt.md` (этапы 4–8).
- **Фаза 3 (клиент):** выход только после завершения теста, отправка `blur` на `/events/`, блокировка горячих клавиш внутри окна.
